### Stage 2 — quality

**K-01 · Low · Fix now → T46**

- **Finding:** a save that resolves after the editor was reset or set up again writes the old invoice's id, number, status, loaded dates and dates into the new editor session.
- **Scenario:**
  1. A save of invoice A is in flight.
  2. The user goes Back, so `reset()` runs, and then opens `/invoices/new`, which runs `initialize()`.
  3. A's response resolves and `applySavedInvoice` sets `invoiceId: A`.
  4. The next Save on the new-invoice screen calls `updateInvoice(A, …)` and overwrites A with the new form.
- **Already there before this range:** `invoiceId`, `invoiceNumber` and `status` were already written this way.
- **What this range adds:** `loadedDates` and the dates join the same unguarded write.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:101-130`, called at `:463,:472`.
- **AC:** AC-12, AC-19; ADR-0009 "Editor save".
- **Suggested:**
  - Hold a session token: `initialize` and `reset` change it.
  - `applySavedInvoice` and `handleSaveFailure` return early when the token captured at the start of `saveInvoice` no longer matches.
  - Add a store test: start a save, call `reset()` + `initialize({})`, resolve the save, then assert that `invoiceId` and `loadedDates` are still unset.

**K-02 · Low · Fix now → T46**

- **Finding:** an invoice number or status changed while a save is in flight is silently replaced by the saved value, and the form stays dirty.
- **Scenario:** the user changes Status after clicking Save.
  - The screen reverts to the old status, but the Save button stays enabled.
  - The next Save sends the old status.
- **Doc mismatch:** the comment at `:99-100` says an in-flight edit is "neither lost nor unguarded", but that holds only for the dates.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:109-112,124`.
- **AC:** AC-06, AC-11.
- **Suggested:**
  - Apply the compare-with-`submitted` rule of `storedOrEdited` to `invoiceNumber` and `status`.
  - Extend the in-flight test to cover both fields.

**K-03 · Low · Fix now → T46**

- **Finding:** `types.ts` imports `LoadedDates` from `./helpers` in the middle of the file, while `helpers.ts` imports from `./types`.
- **Impact:** this is a type-only cycle that goes against the store convention. Shared shapes live in `types.ts`, and imports go at the top.
- **Cite:** `store/invoice-editor-store/types.ts:66`; `store/invoice-editor-store/helpers.ts:12-20`.
- **AC:** n/a.
- **Suggested:** move `interface LoadedDates` into `types.ts`.

**J-01 · Low · Fix now → T47**

- **Finding:** `isMcpUrl` strips only trailing slashes, so the Sentry scrub and the body ignore miss `//api/mcp` and `/api//mcp`.
- **Scenario:**
  1. An Assistant client has the base URL `https://app.example/` and joins `/api/mcp` onto it, which produces `//api/mcp`.
  2. Next 308-redirects the request (`next/dist/server/base-server.js:574-581`).
  3. A sampled transaction or an error event for that request keeps `Authorization: Bearer ifk_…`.
- **Cite:** `sentry.server.config.ts:85`; `tests/unit/config/mcp-sentry-transactions.test.ts:39`.
- **AC:** n/a (sad §8 logging; the I-03 residual).
- **Suggested:**
  - Collapse runs of `/` and `\` before comparing.
  - Add `//api/mcp` and `/api//mcp` to the `it.each`.
