### Stage 1 — AC compliance

**N-04 · Low · Fix now → T50**

- **Finding:** the AC-12 component row does not describe the stale-session cases that T48 added.
- **Cite:** `docs/features/mcp-server/test-plan.md:97`, against tests at `tests/component/invoice-editor-store-loaded-dates.test.tsx:205-303`.
- **AC:** AC-12 (traceability only).
- **Suggested:** extend the row with these cases:
  - a late failure still toasts without Retry
  - a sender switch in flight keeps the number empty
  - a late sender hint or a stale Retry writes nothing
  - a late save does not clear another session's `isSaving`
  - Retry in the same session saves again, but not while a save is in flight

### Stage 2 — quality

**N-01 · Low · Fix now → T50**

- **Finding:** the test "a sender hint that resolves after reset() is not written" passes without the session-token check it was written for.
- **Why:** `reset()` sets `senderProfileId` back to `''`, so the profile-id check alone stops the write. Removing `token === sessionToken` from `:314` leaves the suite green.
- **Uncovered case:**
  1. The user picks sender B in editor X and leaves.
  2. Editor Y opens with sender B and an empty number.
  3. X's late hint is written into Y.

  The impact is small, because the hint depends only on the profile id.
- **Cite:** `tests/component/invoice-editor-store-loaded-dates.test.tsx:261-272`; `store/invoice-editor-store/use-invoice-editor-store.ts:314`.
- **AC:** n/a (r5 M-04a).
- **Suggested:** after `reset()`, call `initialize` with `senderProfileId: 'profile-b'` and `invoiceNumber: ''`, resolve the hint, and assert `invoiceNumberHint` is `undefined`.

**N-02 · Low (pre-existing, from b7e2695) · Fix now (guard) → T50; URL part deferred to spec §8**

- **Finding:** the Retry action on a `FAILED` toast ignores `isSaving`.
- **Scenario:**
  1. A create fails with `FAILED`, and the toast offers Retry.
  2. The user clicks Save. The header button is disabled while the save is in flight, but the toast stays visible.
  3. The user clicks Retry.
  4. The token matches, so a second `createInvoice` runs, and two invoices are created.
- **Second problem:** a create that succeeds through Retry skips `performSave`, so the URL is never moved to the edit route (`hooks/use-editor-header-buttons.tsx:106-115`). The owner deferred this part (spec §8).
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:494-497`. This closure was rewritten in this range.
- **AC:** n/a.
- **Suggested:** `if (token === sessionToken && !get().isSaving) void get().saveInvoice(options);`, plus a test with a save in flight in which Retry does not call the action a second time.

**N-03 · Low · Fix now → T50**

- **Finding:** the Retry guard has no positive test.
- **Effect:** inverting the guard or turning it into a no-op leaves the suite green, which would silently break Retry for every `FAILED` save.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:494-497`. The only Retry test is the stale one, at `invoice-editor-store-loaded-dates.test.tsx:290-303`.
- **AC:** n/a.
- **Suggested:** add a test in which the save fails with `FAILED` and Retry is then invoked in the same session, with no reset. Assert that `updateInvoiceMock` is called twice.

- **Stale success:** a success that resolves after the editor was reset writes nothing.
