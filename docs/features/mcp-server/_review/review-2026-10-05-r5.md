### Stage 2 — quality

**M-01 · Low · Fix now → T49**

- **Finding:** `isMcpUrl` misses a percent-encoded path, which Next still routes to the MCP handler in production.
- **Scenario:**
  1. A request for `/api/%6Dcp` or `/%61pi/mcp` carries `Authorization: Bearer ifk_…`.
  2. In production, Next matches the decoded path when the raw one has no match, so the request reaches `app/api/mcp/route.ts`. There is no 308 redirect, unlike `//api/mcp`.
  3. `isMcpUrl` returns `false`, so an error event or a sampled transaction keeps the header and the body.
- **Not affected:** case variants (`/API/MCP`) 404, because Next routing is case-sensitive.
- **Cite:** `sentry.server.config.ts:86-88`; `node_modules/next/dist/server/lib/router-utils/filesystem.js:489-491`.
- **AC:** n/a (sad §8; the J-01/I-03 residual).
- **Suggested:**
  - Run `decodeURIComponent` on the pathname before collapsing `[/\\]+`.
  - If decoding throws, treat the URL as MCP, so the check fails closed.
  - Add `/api/%6Dcp` and `https://app.example/%61pi/mcp` to the `it.each` (`mcp-sentry-transactions.test.ts:51-56`) and to the ignore asserts (`:88-92`).

**M-02 · Low · Fix now → T48**

- **Finding:** a save that fails after a reset is now completely silent, while one that succeeds still shows a toast.
- **Scenario:**
  1. The user clicks Save on invoice A.
  2. While the save is in flight, they leave the editor, so `reset()` bumps the token.
  3. The save returns `FAILED` or `VALIDATION`, and `handleSaveFailure` returns at `:71` before any toast.
  4. The user gets no sign that the save was not stored. Before this range a failure toast did fire.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:71` vs `:486,:495`.
- **AC:** n/a (editor save feedback).
- **Suggested:**
  - When the token does not match, still show `toast.error(result.error || 'Error saving invoice.')`, without the Retry action and without any state write.
  - Assert the stale-failure toast next to the test at `invoice-editor-store-loaded-dates.test.tsx:183-195`.

**L-02 · Low · Fix now → T48**

- **Finding:** if the Freelancer switches the sender profile while a save is in flight, the number the server assigned under the old profile lands in the form under the new one.
- **Scenario:**
  1. An invoice with an empty number is saved, and the server assigns `A-0005` under profile A.
  2. While the save is in flight, the Freelancer picks profile B. `selectSenderProfile` sets `invoiceNumber: ''` on purpose, so that "A's number is never proposed again under B" (`:270-271`).
  3. The current `''` equals the submitted `''`, so `storedUnlessEdited` writes `A-0005` into a form whose `senderProfileId` is B.
  4. The next Save sends A's number under B as if the Freelancer had typed it.
- **Not a regression:** the code before this range overwrote the number in every case. K-02 narrowed the gap but left this case open.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:123-131`, with `:272-276`.
- **AC:** n/a (K-02 residual).
- **Suggested:**
  - Treat `invoiceNumber` as edited when `state.formData.senderProfileId !== submitted.senderProfileId`, and keep the current `''`.
  - Extend the in-flight test (`invoice-editor-store-loaded-dates.test.tsx:149`) with a sender-profile switch.

**M-03 · Low · Fix now → T48**

- **Finding:** the new `isSaving` guard in `finally` has no test.
- **Scenario:**
  1. A save of A is in flight.
  2. `reset()` and `initialize()` run, and a save of B starts (`isSaving: true`).
  3. A resolves.
  4. Without the guard, `isSaving` drops to `false` while B is in flight, and the Save button (`hooks/use-editor-header-buttons.tsx:197`) allows a second concurrent save.
- **Gap:** reverting `:506` to an unconditional `set({ isSaving: false })` leaves the whole suite green.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:506`.
- **AC:** n/a.
- **Suggested:** add exactly that sequence as a test, and assert `isSaving === true` after A resolves.

**M-04 · Low (pre-existing) · Fix now → T48**

- **Finding:** two other async write paths in the store still write after a reset without a token check.
  - (a) `selectSenderProfile` writes `invoiceNumberHint` at `:299`. If the user picks B and then C quickly, or picks a sender and then opens another editor, B's proposed number can show as the hint. This is display-only; the hint is never submitted.
  - (b) The Retry action on a `FAILED` toast (`() => get().saveInvoice(options)`, `:478`) saves editor B's form, carrying A's `confirmedTotals`, when it is clicked after the user navigated to B.
- **Not in the store:** there is no autosave, status-change or delete path; status changes go through the synchronous `updateField`.
- **Cite:** `store/invoice-editor-store/use-invoice-editor-store.ts:299,478`.
- **AC:** n/a.
- **Suggested:** capture `sessionToken` in both closures and no-op when it does not match.
